Descripción del proyecto

Objetivo

Smartruck es una plataforma logística para la publicación, cotización, gestión y desbloqueo de ofertas de carga, con pagos integrados.

Se desarrolla en el marco de Trabajo Profesional (FIUBA). En esta sección se documentan el problema, los objetivos del sistema y el alcance de la entrega.

Portales

  • Dador (smartruck-dador): publica cargas, cotiza, gestiona ofertas y sigue pagos.
  • Transportista (smartruck-transportista): busca cargas, calcula viajes, desbloquea ofertas con pago y gestiona flota y viajes.
  • Backoffice (smartruck-backoffice): administración de usuarios, verificación de documentos y rol ADMIN.
  • Landing (landing-page): sitio público con derivación al dador y al transportista.

Los tres portales autenticados usan TanStack Start + React. Cada uno consume tres servicios por separado, sin pasar por el backend para todo:

DestinoQué consume el portalCómo llega
Supabase AuthSesión y JWT del usuarioVITE_SUPABASE_URL y VITE_SUPABASE_ANON_KEY
GeoserviceRutas, distancias, catálogo de localidades, autocompletado de ciudades y asociación del pin a la localidad más cercanaVITE_GEO_SERVICE_API, o el hostname de Cloudflare según VITE_APP_ENV
BackendCargas, ofertas, pagos, documentos y perfilVITE_SMARTRUCK_BACKEND_API por API Gateway

El frontend no calcula distancias ni estimaciones: cuando Geoservice no responde, la interfaz muestra "distancia no disponible".

Borde

  • Cloudflare: DNS de smartruck.tech, TLS y rate limiting sobre el endpoint de rutas (120 req/min por IP y host, con ventana de 10 s).
  • Geoservice (Cloudflare Worker, TypeScript; repositorio): dueño de la geografía de la plataforma.
    • Endpoints: /geo/routes (y el alias legacy /routes), /geo/routes/batch, /geo/localities (búsqueda, resolve, nearest y catalog), /geo/health y /geo/version.
    • Catálogo cerrado de 24 provincias y 150 localidades con coordenadas, y 11.175 rutas precargadas con trazado vial.
    • Cascada de resolución: caché de Cloudflare (caches.default) → tabla routes del schema geo en Supabase (vía PostgREST con supabase-js) → proveedor Mapbox Directions (si hay token) → estimación geodésica marcada con is_estimation.
    • Los proveedores y las estimaciones no se cachean (no-store).
    • AUTH_REQUIRED=true exige un JWT de Supabase (ES256, JWKS, audience=authenticated); los healthchecks y /version quedan públicos.
  • API Gateway (GCP): expone el backend en HTTPS y lo invoca con run.invoker sobre Cloud Run privado.

Geoservice tiene dos consumidores, y ninguno pasa por el API Gateway: el frontend lo llama por el hostname de Cloudflare con la sesión del usuario, y el backend lo llama con su propia credencial de servicio para cotizar y para sincronizar el catálogo de localidades.

Núcleo

smartruck-backend es un monolito hexagonal en Python 3.12 con FastAPI, SQLModel y Alembic sobre PostgreSQL (Supabase). El código se organiza en:

CapaRol
domain/Modelos, puertos, excepciones y reglas de negocio.
application/Casos de uso, DTOs y LogManager.
infrastructure/inbound/Adaptadores de entrada: HTTP controllers, DTOs, mappers y middlewares.
infrastructure/outbound/Adaptadores de salida: persistencia PostgreSQL, Storage, gateways de pago y clientes HTTP.

Agrupa funcionalmente identidad y perfiles, cargas y cotizaciones, pagos y desbloqueo, y documentos y confianza. Corre en Cloud Run privado detrás del API Gateway.

Datos e integraciones

  • Supabase Auth: emite JWT firmados con ES256 y publica JWKS.
  • Supabase PostgreSQL: datos de negocio, tabla local con los ids válidos de localidad y schema geo con provincias, localidades y rutas que consume Geoservice.
  • Supabase Storage: bucket privado documents; el backend firma URLs de subida y de lectura.
  • MercadoPago: Checkout Pro, webhook y consulta de pagos.
  • Mapbox: geocodificación y Directions. Nominatim: fallback de geocodificación.

Observabilidad

  • El backend emite logs JSON a stdout con LogManager. Un middleware agrega un correlation ID por request.
  • En Cloud Run, los logs van a Cloud Logging y se reenvían por Pub/Sub y Dataflow a Datadog (us5).
  • Los portales desplegados en Render envían sus logs a Datadog mediante un log stream de workspace.

Flujos principales

Autenticación y autorización

  1. Supabase Auth emite un JWT ES256 para el usuario.
  2. Los frontends envían Authorization: Bearer <token> a VITE_SMARTRUCK_BACKEND_API.
  3. El backend valida firma, issuer y vigencia contra el JWKS de Supabase. El backoffice exige además rol ADMIN.
  4. Geoservice valida el mismo JWT cuando AUTH_REQUIRED=true; los endpoints de salud y versión quedan públicos.

Cotización, publicación y ruteo

Hay tres caminos distintos según la operación:

  • Consultar rutas o distancias en la interfaz: el frontend llama a Geoservice por el hostname de Cloudflare con la sesión del usuario, y usa el catálogo de localidades embebido en el build. La distancia no se calcula en el cliente.
  • Cotizar (POST /loads/quote): QuoteLoadUseCase usa el puerto RouteDistance a través de RoutesServiceDistance, que llama a Geoservice (ROUTES_SERVICE_BASE_URL). El precio sugerido sale de Pricing.
  • Publicar (POST /loads/offerer/{offerer_id}): CreateLoadUseCase resuelve origen y destino con LocationResolver y guarda ids de localidad (origin_locality_id, destination_locality_id), no nombres ni distancias. El backend valida esos ids contra su tabla local de ids válidos.

La carga es una referencia al catálogo, no una copia: la distancia y el trazado se leen siempre desde Geoservice, de modo que cotizar y mostrar coinciden.

Búsqueda de cargas

SearchLoadsUseCase (expuesto como POST /loads/search) resuelve el matching de forma naive: obtiene todas las localidades y todas las cargas, filtra las activas, calcula distancias con haversine × 1.25 y puntúa en memoria. No usa PostGIS ni la vista matching_loads. La mejora con poda espacial y scoring sobre el servicio geográfico es trabajo abierto del backend.

Desbloqueo y pago

Figura 2. Camino crítico desde la creación de la preferencia de pago hasta la reserva de la carga. Versión editable: SVG.

  1. El transportista bloquea la oferta (POST /loads/{load_id}/transporters/{transporter_id}/lock) y consulta el costo de desbloqueo (GET /loads/{load_id}/unlock-fee).
  2. El frontend pide el pago (POST /payments). El backend crea un Payment en estado PENDING y una preferencia en MercadoPago Checkout Pro, y devuelve checkout_url.
  3. El transportista paga en Checkout Pro. MercadoPago envía el webhook POST /payments/mercadopago/webhook; el backend valida la firma y consulta el pago al proveedor.
  4. El frontend reconcilia con POST /payments/{payment_id}/sync.
  5. El transportista confirma el desbloqueo (POST /loads/{load_id}/transporters/{transporter_id}/unlock). UnlockLoadUseCase revalida contra MercadoPago el estado, la referencia externa, el importe y la moneda; recién entonces marca el pago como aprobado y la carga como RESERVED.
  6. El backend crea una notificación in-app para el dador.

El backend no confía en el estado que informa el cliente: la reserva exige un pago efectivamente aprobado por MercadoPago.

Documentos y verificación

  1. El usuario pide una URL de subida (POST /documents/upload-url) y el backend registra la intención y firma la URL.
  2. El cliente sube el archivo directo a Supabase Storage (bucket privado documents).
  3. El cliente confirma (POST /documents/{document_id}/confirm); el backend valida tamaño y tipo.
  4. El usuario puede obtener una URL de lectura firmada (GET /documents/{document_id}/read-url); el backoffice verifica los documentos desde sus propios endpoints de administración.

Trabajo pendiente

  • El matching del backend sigue puntuando en memoria; la mejora es Postgres con PostGIS y el lote de Geoservice.
  • Sin circuit breaker ni pooling HTTP en RoutesServiceDistance (usa urllib).
  • Sin PWA ni service worker en los portales.

Flujo de trabajo

  1. Las historias viven en el Board de roadmap, con sus criterios de aceptación como escenarios Gherkin (Plantilla de ticket).
  2. Antes de empezar, la historia cumple el Definition of Ready y pasa a In progress.
  3. Se trabaja en main, sin ramas de feature ni pull requests, con commits atómicos y un push por commit (Conventional Commits).
  4. Con la feature terminada, se libera a test con ./scripts/release_to_test patch|minor|major y la historia pasa a In review con las horas insumidas (Workflow de entrega).
  5. Al final del sprint, el equipo libera a prod con ./scripts/release_to_prod y las historias pasan a Done (Definition of Done).

Jerarquía de trabajo

Todo el trabajo se modela como user stories en el repo smartruck-ar/roadmap, agrupadas en épicas (milestones) y planificadas en el Board del sprint. No hay tasks: cada historia se trabaja directamente en el repo de producto que corresponde.

Modelo

Épica       milestone de roadmap         D.2 - Gestión de carga
  └── Historia   issue "user story"      D.2.8 - Como dador, Quiero …, Para …
        ├── Contraparte de UI            UI-D.2.8 - Como dador, Quiero …, Para …
        └── Sub-historia (sub-issue)     D.2.8.1 - …

La historia de backend y su contraparte de UI comparten el número: el contador es único por milestone. Una vez numerado, el título no cambia.

Qué lleva cada nivel

Épica (milestone)

  • Objetivo de negocio amplio que agrupa historias.
  • No se estima ni tiene repositorio.

Historia (user story)

  • Título Como …, Quiero …, Para …; la automatización le agrega el número y el label user story.
  • Backend: los criterios de aceptación son sus escenarios Gherkin (Plantilla de ticket).
  • UI (UI-): referencia la historia de backend asociada.
  • En el Board lleva Status, Sprint, US Points, Priority, Estimate (hs) y Spent (hs).
  • Se trabaja en el repo de producto que corresponde, en main (Workflow de entrega).

Spike

  • Investigación o decisión con un entregable concreto (documento o decisión), sin código de producto.
  • Milestone SPIKES y label spike. Gherkins: no aplica.

Definition of Ready (DoR)

Una historia solo entra a desarrollo si cumple este checklist. Recién ahí pasa a Ready en el Board.

Historia lista para trabajar (Ready)

  • Issue en roadmap con milestone y número asignado por la automatización
  • Título Como …, Quiero …, Para … y contexto en la descripción (Plantilla de ticket)
  • Backend: Gherkins pusheados a main del repo y link al .feature en la descripción
  • UI: referencia a la historia de backend asociada
  • US Points cargados (Estimación)
  • Priority asignada
  • Dependencias declaradas (Bloqueado por #<N>) y desbloqueadas

Gherkins

En una historia de backend, los criterios de aceptación son sus escenarios Gherkin. Los .feature tienen que estar pusheados a main antes de considerarla Ready, y la descripción tiene que tener el link al archivo. El formato del feature sigue la Convención de Gherkin. Si no aplica (spike), indicar Gherkins: no aplica.

Ciclo de vida en la descripción de una user story de backend: al crearla, los escenarios van escritos en la descripción; antes de Ready se pushean a main; una vez en main, el bloque se reemplaza por el link al .feature. Detalle en Plantilla de ticket.

Al comenzar la historia

  • Pasarla a In progress en el Board
  • Cargar Estimate (hs) (horas hombre previstas)

Eso es distinto de los US points: los puntos son esfuerzo relativo; las horas son la estimación temporal al arrancar.

Definition of Done (DoD)

Una historia está Done cuando está en ambiente productivo. Una épica está Done cuando todas sus historias lo están.

Regla de oro

Done = en productivo (además de cumplir CA y tests). Productivo se libera a mano, con el equipo, al final del sprint (Workflow de entrega).

NivelDone cuando…
HistoriaEstá desplegada en productivo y cumple el checklist de abajo

Historia Done

  • Cumple todos los criterios de aceptación (escenarios Gherkin en verde, sin @wip)
  • Código pusheado a main del repositorio asociado
  • Tests acordados en verde (incl. aceptación / Gherkin si aplica)
  • Validada en test (historia en In review)
  • Desplegada en ambiente productivo con el release del sprint
  • Spent (hs) cargado con las horas hombre insumidas
  • README del repo y docs actualizados si aplica

  • Número de la historia en el scope de los commits (Conventional Commits)

Workflow de entrega

Cómo una historia pasa de Ready a producción. No hay ramas de feature ni pull requests: se trabaja en main y los ambientes se mueven con los scripts de release.

Quick path

  1. Tomar una historia Ready del Board y pasarla a In progress.
  2. Implementar en main, con commits atómicos y un push por commit (Conventional Commits).
  3. Con la feature terminada y la suite en verde, liberar a test: ./scripts/release_to_test patch|minor|major.
  4. Con el pipeline de test en verde, pasar la historia a In review y cargar las horas insumidas.

Convención de logging (arquitectura hexagonal)

Dónde y qué loguear en los servicios SmartTruck (backend y fronts con capas hexagonales).

Los logs se emiten con LogManager (application/logger/): JSON a stdout. La recolección (Datadog, Loki, etc.) es responsabilidad de la infraestructura, no de un provider en la app. Convención de carpetas: Arquitectura backend.

En smartruck-backend, los controllers/repos de infrastructure inyectan LogManager (desde application.logger). Cada controller y cada repositorio lo recibe por Depends (por ejemplo trucks_controller.py y PostgreSQLTruckRepository); este módulo solo provee el mecanismo.

API (sin secretos)

LogManager(service="smartruck-backend", env="test").info("…")
LogManager(service="smartruck-backend", env="test").error("…")

Niveles disponibles: fatal, error, warn, info, debug, trace.

NivelUso
infoQué se está haciendo en bordes (entrada/salida, datos salientes seguros)
error / warn / fatalFallos y advertencias (p. ej. GlobalExceptionHandler)
debug / traceSolo para depurar; no para flujo de negocio habitual

Solo message: str. No hay parámetros password, token ni similares: no loguear secretos en el mensaje.

Correlation ID

  • Header: X-Correlation-Id
  • Middleware: reutiliza el header o genera un UUID; lo refleja en la response.
  • LogManager lo incluye en el JSON cuando está disponible (correlation_id).

Dónde loguear

Solo en los bordes del hexágono: entradas y salidas.

LugarRol en el hexágonoQué loguea
Controladores (adapters de entrada / HTTP)Entradainfo de lo que se está haciendo (request / caso, sin secretos)
Repositorios (adapters de salida / persistencia u otros gateways)Salidainfo de operaciones hacia afuera
GlobalExceptionHandlerBorde HTTPerror/warning de excepciones burbujeadas + response HTTP
[HTTP] → Controlador ──info────────────┐
              │                        │
              ▼                        ├──> stdout → Datadog / audit
         Caso de uso                   │
              │                        │
              ▼                        │
         Repositorio ──info────────────┤
              │                        │
              └── excepciones ──► GlobalExceptionHandler ──error─┘

Errores y excepciones

  • Las excepciones burbujean hasta un GlobalExceptionHandler (capa HTTP / inbound).
  • El handler centraliza: log error/warning, mapeo a response HTTP. Los controllers no atrapan para relanzar.
  • Controllers: solo info de entrada (y datos seguros). Repos: info de salida; propagan errores hacia arriba.
  • No duplicar el log de error en repo y controller y handler.

Info / “qué se está haciendo”

  • Controlador: entrada al caso (ej. “crear viaje”, IDs relevantes, sin secretos).
  • Repositorio: operación de salida (ej. “persistir load”, “buscar oferente por email”).
  • Preferir mensajes estructurados (JSON) con service, env, level, y contexto útil (request_id si existe).

Qué no loguear ahí

EvitarMotivo
Loguear en cada línea del caso de uso / dominioRuido; el dominio queda limpio
Loguear el mismo error en repo y controller y handlerDuplicado; el error se loguea una sola vez en el GlobalExceptionHandler
Passwords, tokens, PII innecesariaSeguridad

Checklist

  • info en controlador (entrada) y repositorio (salida)
  • Errores/excepciones logueados en el GlobalExceptionHandler (no catch/rethrow en controllers)
  • Sin logs de negocio ruidosos en application/domain
  • Salida a stdout (JSON vía LogManager)
  • Sin passwords/tokens en la API ni en el contenido del mensaje

Automatización de historias (roadmap)

Cómo crear una historia de usuario y qué formas hay de que el propio repositorio la numere, la etiquete y arme la contraparte de front/back automáticamente.

Repo: todo esto pasa en smartruck-ar/roadmap. Nunca en smartruck-backend, smartruck-dador, smartruck-transportista ni ningún otro repo de producto — esos repos no tienen esta automatización.

Implementación: .github/workflows/auto-number-issues.yml + scripts/auto_number_issues.py, corriendo en el runner self-hosted del repo.

Qué dispara la automatización

Dos eventos de GitHub sobre una issue de roadmap:

EventoCuándo pasaQué hace
milestonedSe le asigna un milestone a la issueNumera, etiqueta y evalúa si hay que crear una contraparte
labeledSe agrega uno de los tags front+back, crear front o crear backSolo reacciona a esos tres; cualquier otro label (bug, user story, etc.) se ignora

Nada de esto pasa si la issue no tiene milestone asignado.

Comportamiento por defecto (una sola historia)

Al milestonear una historia sin ningún tag especial, la automatización:

  1. La numera: <Prefijo del milestone>.<siguiente número> - <título> (ej. T.2.9 - Como transportista...).
  2. Le agrega el label user story.
  3. La agrega al proyecto Board (#4) y le asigna el sprint actual (según fecha de Argentina).

Esto es todo. No crea ninguna otra historia. Si querés una contraparte de front o de back, tenés que pedirla explícitamente con los tags de la sección siguiente.

El item queda con Status: Backlog (el default de GitHub para un item nuevo). Movelo vos a Ready/In progress en el Board — la automatización no lo hace.

¿Cómo indico si la historia es de backend o de UI?

No hay un tag para esto: se define con el título, antes de milestonear.

  • Backend (default): título normal, sin prefijo. Ej: Como transportista, Quiero filtrar cargas... → queda T.2.9 - Como transportista....
  • UI: escribí el título arrancando con UI-. Ej: UI-Como transportista, Quiero filtrar cargas... → queda UI-T.2.9 - Como transportista....

El número (T.2.9) sale de un contador compartido por milestone: da lo mismo si la última historia numerada en ese milestone fue de backend o de UI, la siguiente sigue la secuencia.

Crear las dos historias (back + UI) de una

Si de entrada sabés que la historia necesita pantalla y backend:

  1. Escribí el título (con o sin UI-, según cuál de las dos querés que sea "la original").
  2. Agregале el label front+back (antes o después de milestonear, da igual el orden).
  3. Milestoneala.

Resultado: la historia original queda numerada, y se crea una segunda issue con el mismo número y el prefijo que le falta (si la original era de backend, la nueva es UI-T.2.9 - ...; si la original ya era UI-, la nueva es la de backend). Quedan linkeadas entre sí con un comentario cruzado (🔗 Relacionado con el ticket de UI/backend: #N).

Al terminar, el tag front+back se saca automáticamente de la historia original. Las dos terminan solo con user story.

Agregar la contraparte más tarde

Si ya tenés una historia numerada (de backend o de UI) y después decidís que también necesita la otra mitad, no hace falta recrear nada: agregale el tag correspondiente a la historia que ya existe.

Tengo...Le pongo el tag...Y se crea...
Una historia de backend (T.2.9 - ...)crear frontSu contraparte de UI (UI-T.2.9 - ...), mismo milestone, sprint actual
Una historia de UI (UI-T.2.9 - ...)crear backSu contraparte de backend (T.2.9 - ...), mismo milestone, sprint actual

El tag usado se saca solo al terminar. Si lo ponés en el lado que no corresponde (ej. crear front sobre una historia que ya es de UI), no hace nada más que sacarse el tag — no rompe nada ni duplica.

Si la historia todavía no tiene milestone asignado, el tag no dispara nada (no hay de dónde sacar el número); hay que milestonearla primero.

Milestones de spike (SPIKES, T.SPIKE)

Los spikes son un caso aparte: no se separan por producto (transportista/dador) y nunca generan contraparte, tengan o no alguno de los tags anteriores.

  • Prefijo fijo: S, con un contador único compartido por todos los milestones de spike (no hay S para transportista y otro para dador).
  • Se numeran igual que cualquier historia (S.1 - ..., S.2 - ..., …), reciben user story y sprint actual.
  • Los tags front+back, crear front y crear back se ignoran por completo en un milestone de spike.

Sub-issues (una historia que cuelga de otra)

Si la historia que estás milestoneando es sub-issue de otra issue del propio repo roadmap (relación nativa de GitHub, no un link a mano), hereda el prefijo del padre en vez de calcular uno nuevo a partir del milestone:

Padre  T.1.1  (ya numerada)
  └── Hijo  T.1.1.1, T.1.1.2, …   (siguiente número dentro del padre)

Si el padre todavía no tiene un prefijo numerado (por ejemplo, no fue milestoneado todavía), el hijo se numera como una historia normal a partir del milestone.

Una vez numerada, el título queda fijo

Si el título ya tiene un prefijo numerado (con o sin UI- adelante), la automatización nunca lo recalcula ni lo renombra, sin importar cuántas veces se vuelva a milestonear o etiquetar la issue. Esto es lo que hace seguro:

  • Re-milestonear por error una historia ya numerada (no la duplica ni le cambia el número).
  • Agregar crear front/crear back sobre algo que ya tiene su contraparte (find_existing_companion la detecta por un marcador oculto en el body y no crea una segunda).

  • Verde y beige/blanco siguen siendo los dos colores principales. Se pueden proponer colores adicionales.

Decisiones tomadas

  • Wordmark como texto, no como imagen. El header del dador dejó de usar smartruck-logo.jpg y renderiza el wordmark con el componente compartido src/components/layout/wordmark.tsx, usado tanto por el header autenticado como por el bloque de marca de las vistas públicas. Razón: un JPG escalado en proyector se ve borroso, el texto queda nítido a cualquier tamaño, y el brief pide una fuente propia para el título "Smartruck", cosa que solo aplica a texto. El JPG se mantiene como favicon y og:image.
  • El wordmark es bicolor y oblicuo, como el logo. "Smar" en --brand-blue y "Truck" en --brand-green, en Chakra Petch bold italic (@fontsource/chakra-petch/700-italic.css; Chakra Petch llega hasta 700, no existe el 900). Los dos tramos van en spans adyacentes sin espacio entre sí, para que un lector de pantalla lea una sola palabra.
  • El subrayado de la marca es una "frenada". Al pasar el mouse entra rápido y se asienta: la barra va sesgada a skewX(-10deg) para seguir la itálica y se pasa un 5% antes de volver, así que se lee como un vehículo frenando y no como un barrido. Es el swoosh que ya tiene el logo. Con prefers-reduced-motion aparece sin animación.
  • Cuidado con scale en Tailwind v4. El subrayado está escrito como CSS propio (.wordmark-underline en src/styles.css) y no con utilidades a propósito: Tailwind v4 emite scale-x-* a través de la propiedad independiente scale, que compone con transform, así que un after:scale-x-0 de base cancela cualquier keyframe que anime transform y el subrayado queda invisible. Lo mismo rompe un transition-transform cuando lo que cambia es scale. Lección para el portado: si una animación anima transform, no la mezcles con utilidades de escala.
  • La marca lleva al inicio solo dentro del shell autenticado. En el header es un Link a / con cursor pointer; en el bloque de marca de las vistas públicas queda como texto, sin interacción. El componente Wordmark sigue siendo presentacional: el link está en el Topbar.
  • Los dos colores de marca son los del logo: azul petróleo rgb(10 52 68) = #0a3444 en --brand-blue, y verde oliva rgb(101 105 68) = #656944 en --brand-green. Definidos en oklch() con el rgb de origen en comentario, y registrados como --color-brand-blue / --color-brand-green para que existan las utilidades text-brand-blue / text-brand-green. En modo oscuro los dos se elevan (#6b9aaf y #aab07d): el azul del logo es ilegible sobre una superficie petróleo, así que se conserva el hue y se sube la luminosidad.
  • El primario del dador es un verde más fuerte que el del logo, no el oliva literal. --primary, --ring y las variantes de sidebar usan oklch(0.51 0.1 130) = #53712f (5.57:1 con blanco encima, 4.87:1 contra el fondo); en oscuro oklch(0.64 0.11 130) = #76994f.
  • Distinción importante para el portado: --brand-green sigue siendo el oliva exacto del logo (#656944, hue 113.4), porque es el color de la marca; el primario es su variante de portal, más verde y saturada (hue 130). Si en el transportista se quiere lo mismo, el equivalente es partir del azul del logo y subirlo de la misma forma. Dial del primario: subir el hue hacia 145 da más verde, bajarlo hacia 113 vuelve al oliva literal, y subir el chroma da más intensidad.
  • El primario del transportista será el azul petróleo: rgb(10 52 68) como opción principal (13.23:1 contra blanco) o rgb(57 80 94) = #39505e como alternativa más clara para un look menos duro.
  • Un solo punto de presentación de marca. Si el wordmark cambia, cambia en wordmark.tsx y los dos portales lo heredan.
  • Sin iconos decorativos en headers. Regla aplicada: se retira un icono si al quitarlo no se pierde información; se conserva si codifica dirección o estado. El inventario de lo retirado está abajo.
  • La escala es un único número. html { font-size: 142.9% }. Se eligió escalar la raíz en lugar de redefinir tamaños por componente porque es proporcional y no recorta nada: contenedores, paddings y alturas de control crecen junto con el texto, así que ningún componente necesita ajuste manual. Costo aceptado: menos densidad por pantalla, a cambio de legibilidad en proyector.
  • El modo claro pasa a beige cálido (h≈85) con el verde como primario; el oscuro mantiene el azul petróleo + oliva del logo y resuelve la elevación por capas de superficie en vez de sombras.
  • Se activan las animaciones base de shadcn importando tw-animate-css, que estaba instalado pero nunca importado.
  • El theme-color sigue al modo activo: el hook de tema actualiza el meta al togglear, en vez de quedar fijo en #ffffff.
  • La vista activa se deriva del pathname, no de estado local. NavKey perdió el miembro myLoadDetail: con rutas reales, /my-loads/$loadId ilumina solo el tab myLoads.
  • El guard de sesión vive en el root, no en el layout autenticado. Se evaluó moverlo al layout route y se descartó: el layout solo ve sus hijos, así que una visita sin sesión a una ruta desconocida terminaría en 404 en vez de redirigir a login. El guard necesita ver todas las rutas. Lección para el portado: no reubicar un guard sin comprobar que sigue cubriendo lo mismo.
  • El shell ya no se re-monta al navegar. Ese era el objetivo, pero trae una consecuencia de ciclo de vida a tener en cuenta al portar: la campana de notificaciones y el estado del drawer persisten entre tabs en vez de reiniciarse.
  • Tres roles de radio, y nada más. Pill (rounded-full) para todo lo que se acciona: botones, icon buttons, inputs, selects, badges, avatares, chips, pills de nav, tabs, progreso, slider. Panel (rounded-2xl, 16px) para todo lo que contiene: cards, dialogs, drawers, sheets, popovers, dropdowns, paneles de vista. Inset (rounded-xl, 12px) para lo que va dentro de un panel: tiles de icono, sub-paneles, empty states. Reglas: un elemento un rol, sin overrides de radio en el call site, y un hijo nunca puede quedar más redondo que su contenedor. rounded-3xl ya no existe en el código.
  • Los items de menú son la excepción deliberada: van en rounded-lg (8px), no pill. Son filas de ancho completo con icono y estado seleccionado full-bleed, y una cápsula les come el padding lateral de forma despareja.
  • El Textarea es el único control que no es pill: toma el radio Inset (12px) para que nunca pueda quedar más redondo que la card que lo contiene. Fue la única inversión real que apareció en el pase, y salió de que el contrato original le daba radio Panel.
  • Regla de superficies. El fondo de página es beige (--background, hoy oklch(0.968 0.014 85) = #f9f4ea). Toda superficie que contiene campos va en --card (blanco, #fefbf6), y ningún campo interactivo puede resolver al fondo de página. En el pase el beige venía de tres lados distintos: contenedores con bg-background, selects nativos con bg-background hardcodeado, y —el menos obvio— el variant outline de Button, que fija bg-background y es justo el que usan los triggers de autocomplete y date picker. Se corrigió agregando bg-card al className del trigger (twMerge lo respeta, porque cn(buttonVariants({ ...className })) deja el className último), sin tocar el variant global.
  • Ojo con los px fijos, no solo en tipografía. El knob del 142.9% escala todo lo que es rem, pero un ancho en px queda clavado: el campo de hora tenía w-[95px] y por eso se veía diminuto al lado de campos que sí crecían. Es la misma trampa que los text-[Npx], aplicada a anchos. Al portar, buscar w-[, h-[, max-w-[ y text-[ con valores en px.

Decisiones abiertas

  • Acento por portal: el usuario se inclina por paletas idénticas con el contenido como única diferencia. Hay una propuesta de acento pendiente de aprobación.
  • Mecanismo de escala a unificar en el portado. El dador escala la raíz (142.9%); el transportista ya define tokens --text-* explícitos. Son mecanismos distintos y no conviven sin pisarse: hay que elegir uno antes de portar.
  • El chrome de Leaflet quedó en px a propósito. La geometría de los pins y el ancho del hover card dependen del zoom del mapa, no de la escala de la UI; escalarlos a ciegas cambia su significado. Requiere un pase propio, consciente del zoom.

2. Metodología y dinámica que seguimos (esto es lo que hay que respetar)

  1. Commits atómicos, sin push. Formato conventional commits <type>(<id-task>): <descripción>, con type limitado a feat / fix / refactor. Un commit = un cambio revisable y autoexplicativo. Nada se pushea sin pedido explícito.
  2. Gate de verificación por task, obligatorio. scripts/run_lint + scripts/run_all_tests + npm run build, todo en verde. En Windows los scripts son bash y WSL no trae node: hay que correrlos con Git Bash (& "C:\Program Files\Git\bin\bash.exe" -lc "./scripts/run_all_tests"). CI=true los vuelve check-only (no mutan).
  3. Normalizar ANTES de commitear. El gate corre prettier --write / eslint --fix: si commiteás primero y normalizás después, el árbol queda sucio y hay que rehacer commits.
  4. Los tests de presentación son puntos de decisión, no bloqueantes. Un restyle puede cambiar lo que un test fija, pero entonces el test se actualiza en el mismo commit y a propósito. Lo prohibido es romperlo en silencio. Hay aserciones que fijan implementación y no valor para el usuario y conviene reescribirlas (ejemplo real: un findAllByText("Transportista asignado")).toHaveLength(2) que congelaba una duplicación card/overlay; se cambió a findByText(...) en el commit que deduplicó).
  5. Presentación ≠ comportamiento. El restyling no cambia flujos, validaciones, navegación ni contratos de red. Cuando un pedido sí toca comportamiento (ej. caché), se documenta y se decide aparte.
  6. git status antes de delegar o commitear. Una vez el árbol tenía ediciones sin commitear de una persona y se commiteó sin querer. Si hay cambios que no son tuyos: parar y reportar.
  7. Tokens antes que componentes. Nada de familias crudas de Tailwind (emerald-*, sky-*, …); todo por tokens semánticos en src/styles.css (:root / .dark, mapeados en @theme inline). Nada de px fijos (text-[Npx], w-[Npx], …): la escala se maneja con html { font-size: 142.9% } y todo es rem-based.
  8. Tres roles de radio y nada más: Pill (rounded-full) para lo accionable, Panel (rounded-2xl) para lo que contiene, Inset (rounded-xl) para lo que va dentro de un panel. Un hijo nunca puede quedar más redondo que su contenedor.
  9. Regla de superficies: fondo de página beige (--background), toda superficie que contiene campos en --card, y ningún campo interactivo resolviendo al fondo de página.
  10. Sin iconos decorativos en headers. Se retira un icono si al quitarlo no se pierde información; se conserva sólo si codifica dirección o estado.
  11. Movimiento: sutil, corto y con guarda. Toda animación ≤200ms para feedback de UI, y tiene que degradar bajo la guarda global de prefers-reduced-motion (que ya está en styles.css). Nada de animación que tape un loading o retrase contenido.

4. Cambios pendientes del BACKEND

Los números de línea y nombres de archivo de esta sección salen de relevar el repo smartruck-backend al investigar el bug de hora. Conviene verificarlos contra el código actual antes de implementar.

4.1 Contrato de fechas: normalizar aware → local Argentina naive (CRÍTICO)

Qué pasa. El backend declara las fechas de carga como hora local argentina naive: pickup_date y delivery_deadline se persisten en columnas TIMESTAMP WITHOUT TIME ZONE.

Evidencia relevada:

  • src/infrastructure/outbound/time/system_date_time_provider.py — el "ahora" del dominio es datetime.now(ARGENTINA).replace(tzinfo=None).
  • src/infrastructure/outbound/persistence/models/load.py y migrations/versions/0001_initial_schema.py — columnas sa.DateTime() (naive).
  • El test de aceptación exige eco exacto: test/acceptance/.../crear_oferta_carga_steps.py manda "2026-08-20T08:00:00" y espera el mismo string.

Qué rompía. El portal dador serializaba la hora del picker (wall clock naive) con offset -03:00. Al castear un timestamptz a una columna naive con la sesión en UTC, Postgres guardaba +3h (12:00 → 15:00). El dato quedaba mal persistido (por eso también lo veía mal el transportista, que sólo lee). El bug afectaba toda hora cargada, no sólo el default.

Qué ya se hizo (del lado dador, en smartruck-dador). Se corrigió el serializador para emitir hora local naive sin offset ni Z (toBackendLocalDateTime en src/lib/date.ts, con test unitario). Los envíos nuevos llegan correctos.

Qué falta del lado backend (red de seguridad). El backend sigue aceptando strings con offset de cualquier cliente. La recomendación es un validador de entrada que normalice a hora local argentina naive antes de que el valor llegue al caso de uso. Punto de entrada relevado: src/infrastructure/inbound/http/.../create_load_request.py (pickup_date: datetime, delivery_deadline: datetime).

Comportamiento propuesto:

si el datetime viene aware  → astimezone(America/Argentina).replace(tzinfo=None)
si viene naive              → dejarlo igual (comportamiento actual, no romper clientes)

Criterios de aceptación sugeridos:

  • CA1: un pickup_date con offset (2026-09-20T12:00:00-03:00) se persiste y se devuelve como 2026-09-20T12:00:00 (hora local argentina), no 15:00.
  • CA2: un pickup_date naive sigue comportándose exactamente como hoy (el contrato de eco exacto del test de aceptación no cambia).
  • CA3: aplica a pickup_date y delivery_deadline por igual.
  • CA4: existe un test de aceptación que manda un datetime con offset y verifica el eco; hoy la suite sólo manda naive, que es justamente por lo que el bug no se detectó.

4.2 Backfill de las cargas ya persistidas con +3h

El fix del dador no repara las filas ya guardadas con el offset aplicado. Hay que decidir y ejecutar una migración de datos (o un script acotado) que reste 3h a las fechas de las cargas afectadas, con criterio de alcance claro (ventana temporal / todos los registros) y su propio respaldo. Es una decisión de producto: conviene confirmarla antes de tocar datos.

4.3 Confirmar el mapeo del status bloqueada

Un commit reciente del portal dador (fix(load): update status mapping for 'bloqueada') cambió el mapeo del lado frontend: bloqueada ahora mapea a Publicada y cancelada a Cancelada; además desapareció Bloqueada del mapeo inverso.

Dos consecuencias a chequear con quien lo hizo:

  • Producto: hoy una carga bloqueada se muestra como "Publicada" en el dador. Si eso no es intencional, es un bug de presentación de estado (no de datos).
  • Código: el estado UI Bloqueada y el token --status-bloqueada del dador quedaron inalcanzables (dead code) — hay que decidir si se limpian o si bloqueada debería seguir siendo un estado propio.

Conviene confirmar si el backend emite bloqueada alguna vez y con qué semántica.
