Descripción del proyecto

Objetivo

Smartruck es una plataforma logística para la publicación, cotización, gestión y desbloqueo de ofertas de carga, con pagos integrados.

Se desarrolla en el marco de Trabajo Profesional (FIUBA). En esta sección se documentan el problema, los objetivos del sistema y el alcance de la entrega.

Portales

  • Dador (smartruck-dador): publica cargas, cotiza, gestiona ofertas y sigue pagos.
  • Transportista (smartruck-transportista): busca cargas, calcula viajes, desbloquea ofertas con pago y gestiona flota y viajes.
  • Backoffice (smartruck-backoffice): administración de usuarios, verificación de documentos y rol ADMIN.
  • Landing (landing-page): sitio público con derivación al dador y al transportista.

Los tres portales autenticados usan TanStack Start + React. Cada uno consume tres servicios por separado, sin pasar por el backend para todo:

DestinoQué consume el portalCómo llega
Supabase AuthSesión y JWT del usuarioVITE_SUPABASE_URL y VITE_SUPABASE_ANON_KEY
GeoserviceRutas, distancias, catálogo de localidades, autocompletado de ciudades y asociación del pin a la localidad más cercanaVITE_GEO_SERVICE_API, o el hostname de Cloudflare según VITE_APP_ENV
BackendCargas, ofertas, pagos, documentos y perfilVITE_SMARTRUCK_BACKEND_API por API Gateway

El frontend no calcula distancias ni estimaciones: cuando Geoservice no responde, la interfaz muestra "distancia no disponible".

Borde

  • Cloudflare: DNS de smartruck.tech, TLS y rate limiting sobre el endpoint de rutas (120 req/min por IP y host, con ventana de 10 s).
  • Geoservice (Cloudflare Worker, TypeScript; repositorio): dueño de la geografía de la plataforma.
    • Endpoints: /geo/routes (y el alias legacy /routes), /geo/routes/batch, /geo/localities (búsqueda, resolve, nearest y catalog), /geo/health y /geo/version.
    • Catálogo cerrado de 24 provincias y 150 localidades con coordenadas, y 11.175 rutas precargadas con trazado vial.
    • Cascada de resolución: caché de Cloudflare (caches.default) → tabla routes del schema geo en Supabase (vía PostgREST con supabase-js) → proveedor Mapbox Directions (si hay token) → estimación geodésica marcada con is_estimation.
    • Los proveedores y las estimaciones no se cachean (no-store).
    • AUTH_REQUIRED=true exige un JWT de Supabase (ES256, JWKS, audience=authenticated); los healthchecks y /version quedan públicos.
  • API Gateway (GCP): expone el backend en HTTPS y lo invoca con run.invoker sobre Cloud Run privado.

Geoservice tiene dos consumidores, y ninguno pasa por el API Gateway: el frontend lo llama por el hostname de Cloudflare con la sesión del usuario, y el backend lo llama con su propia credencial de servicio para cotizar y para sincronizar el catálogo de localidades.

Núcleo

smartruck-backend es un monolito hexagonal en Python 3.12 con FastAPI, SQLModel y Alembic sobre PostgreSQL (Supabase). El código se organiza en:

CapaRol
domain/Modelos, puertos, excepciones y reglas de negocio.
application/Casos de uso, DTOs y LogManager.
infrastructure/inbound/Adaptadores de entrada: HTTP controllers, DTOs, mappers y middlewares.
infrastructure/outbound/Adaptadores de salida: persistencia PostgreSQL, Storage, gateways de pago y clientes HTTP.

Agrupa funcionalmente identidad y perfiles, cargas y cotizaciones, pagos y desbloqueo, y documentos y confianza. Corre en Cloud Run privado detrás del API Gateway.

Datos e integraciones

  • Supabase Auth: emite JWT firmados con ES256 y publica JWKS.
  • Supabase PostgreSQL: datos de negocio, tabla local con los ids válidos de localidad y schema geo con provincias, localidades y rutas que consume Geoservice.
  • Supabase Storage: bucket privado documents; el backend firma URLs de subida y de lectura.
  • MercadoPago: Checkout Pro, webhook y consulta de pagos.
  • Mapbox: geocodificación y Directions. Nominatim: fallback de geocodificación.

Observabilidad

  • El backend emite logs JSON a stdout con LogManager. Un middleware agrega un correlation ID por request.
  • En Cloud Run, los logs van a Cloud Logging y se reenvían por Pub/Sub y Dataflow a Datadog (us5).
  • Los portales desplegados en Render envían sus logs a Datadog mediante un log stream de workspace.

Flujos principales

Autenticación y autorización

  1. Supabase Auth emite un JWT ES256 para el usuario.
  2. Los frontends envían Authorization: Bearer <token> a VITE_SMARTRUCK_BACKEND_API.
  3. El backend valida firma, issuer y vigencia contra el JWKS de Supabase. El backoffice exige además rol ADMIN.
  4. Geoservice valida el mismo JWT cuando AUTH_REQUIRED=true; los endpoints de salud y versión quedan públicos.

Cotización, publicación y ruteo

Hay tres caminos distintos según la operación:

  • Consultar rutas o distancias en la interfaz: el frontend llama a Geoservice por el hostname de Cloudflare con la sesión del usuario, y usa el catálogo de localidades embebido en el build. La distancia no se calcula en el cliente.
  • Cotizar (POST /loads/quote): QuoteLoadUseCase usa el puerto RouteDistance a través de RoutesServiceDistance, que llama a Geoservice (ROUTES_SERVICE_BASE_URL). El precio sugerido sale de Pricing.
  • Publicar (POST /loads/offerer/{offerer_id}): CreateLoadUseCase resuelve origen y destino con LocationResolver y guarda ids de localidad (origin_locality_id, destination_locality_id), no nombres ni distancias. El backend valida esos ids contra su tabla local de ids válidos.

La carga es una referencia al catálogo, no una copia: la distancia y el trazado se leen siempre desde Geoservice, de modo que cotizar y mostrar coinciden.

Búsqueda de cargas

SearchLoadsUseCase (expuesto como POST /loads/search) resuelve el matching de forma naive: obtiene todas las localidades y todas las cargas, filtra las activas, calcula distancias con haversine × 1.25 y puntúa en memoria. No usa PostGIS ni la vista matching_loads. La mejora con poda espacial y scoring sobre el servicio geográfico es trabajo abierto del backend.

Desbloqueo y pago

Figura 2. Camino crítico desde la creación de la preferencia de pago hasta la reserva de la carga. Versión editable: SVG.

  1. El transportista bloquea la oferta (POST /loads/{load_id}/transporters/{transporter_id}/lock) y consulta el costo de desbloqueo (GET /loads/{load_id}/unlock-fee).
  2. El frontend pide el pago (POST /payments). El backend crea un Payment en estado PENDING y una preferencia en MercadoPago Checkout Pro, y devuelve checkout_url.
  3. El transportista paga en Checkout Pro. MercadoPago envía el webhook POST /payments/mercadopago/webhook; el backend valida la firma y consulta el pago al proveedor.
  4. El frontend reconcilia con POST /payments/{payment_id}/sync.
  5. El transportista confirma el desbloqueo (POST /loads/{load_id}/transporters/{transporter_id}/unlock). UnlockLoadUseCase revalida contra MercadoPago el estado, la referencia externa, el importe y la moneda; recién entonces marca el pago como aprobado y la carga como RESERVED.
  6. El backend crea una notificación in-app para el dador.

El backend no confía en el estado que informa el cliente: la reserva exige un pago efectivamente aprobado por MercadoPago.

Documentos y verificación

  1. El usuario pide una URL de subida (POST /documents/upload-url) y el backend registra la intención y firma la URL.
  2. El cliente sube el archivo directo a Supabase Storage (bucket privado documents).
  3. El cliente confirma (POST /documents/{document_id}/confirm); el backend valida tamaño y tipo.
  4. El usuario puede obtener una URL de lectura firmada (GET /documents/{document_id}/read-url); el backoffice verifica los documentos desde sus propios endpoints de administración.

Trabajo pendiente

  • El matching del backend sigue puntuando en memoria; la mejora es Postgres con PostGIS y el lote de Geoservice.
  • Sin circuit breaker ni pooling HTTP en RoutesServiceDistance (usa urllib).
  • Sin PWA ni service worker en los portales.

Riesgos del proyecto Smartruck

Criterio de inclusión

Un ítem entra en la Tabla A solo si cumple las dos condiciones:

  1. Puede producir un resultado negativo de negocio o de operación (plata, carga, reputación, cobertura, confianza, disponibilidad, datos).
  2. No está ya decidido y planificado en un ADR o en el backlog. Si hay una decisión tomada, el ítem va a la Tabla B.

Un bug que no cambia el resultado comercial se trata como incidencia y no entra.

Se conserva el criterio de la propuesta original:

Riesgos de negocio y técnicos

Ordenados por severidad, de más grave a menos grave.

🔴 R-16 — No hay garantía ni seguro de carga: el puenteo es el camino por defecto

  • Probabilidad: Alta · Impacto: Crítico · Semáforo: 🔴

Evidencia: la propuesta justificaba el modelo "la plataforma no intermedia en el flete" con un blindaje de pólizas de seguro por viaje. En el sistema implementado no hay emisión de póliza ni servicio de seguro: lo único relacionado es un tipo de documento que el usuario puede subir (INSURANCE_POLICY, smartruck-backend/src/domain/models/document.py:9). Tampoco hay escrow, ni prueba de entrega por viaje, ni garantía de pago del flete.

Qué pasa en el negocio: la razón por la que un transportista dejaría de usar un grupo de WhatsApp —que la transacción tenga respaldo— no existe. El unlock fee es un costo puro frente a un WhatsApp gratuito. Salvo que la reputación dentro de la plataforma tenga valor real, el camino racional es cerrar el trato fuera y volver al grupo: el riesgo de tercerización no se mitigó, se volvió el comportamiento por defecto. Lo único que empuja a quedarse es la reputación, y esa reputación depende de viajes que el producto no puede garantizar (R-15).

Mitigación: sostener la promesa con lo que sí se controla —verificación obligatoria de ambos lados, historial visible con reseñas atadas a evidencia— y dejar la póliza por viaje como objetivo de mediano plazo, financiada con parte del fee.

🔴 R-11 — El bloqueo de oferta no tiene vencimiento ni valida el estado previo

  • Probabilidad: Alta · Impacto: Crítico · Semáforo: 🔴

Evidencia: LockLoadUseCase.lock no mira el estado actual de la carga: la marca bloqueada y le asigna el transportista que viene en la URL (smartruck-backend/src/application/use_cases/loads/lock_load_use_case.py:25). No hay TTL ni marca de tiempo. La liberación depende de que el cliente llame explícitamente a abort-lock, algo que solo ocurre si el transportista cierra el drawer (smartruck-transportista/src/views/loads/load-drawer.tsx:155). Mientras la carga está bloqueada no aparece en la búsqueda (smartruck-backend/src/application/use_cases/loads/search_loads_use_case.py:109).

Qué pasa en el negocio: el bloqueo sí evita la carrera (la carga desaparece del tablero), pero deja dos problemas. Primero: un transportista que abre el checkout y cierra la pestaña deja la oferta fuera del mercado de forma permanente. Segundo: como el bloqueo no valida el estado, un transportista puede bloquear una carga que ya estaba reservada y pagada por otro, pisando la reserva y el pago acreditado. En un tablero con volumen bajo, cada oferta muerta es una venta perdida y una excusa para volver al canal informal.

Mitigación: TTL de bloqueo con liberación automática (por ejemplo 15 minutos, alineado con la expiración de la preferencia de MercadoPago, que ya existe: smartruck-backend/src/infrastructure/outbound/gateways/mercadopago_payment_gateway.py:66); validar la transición activa → bloqueada antes de bloquear.

🔴 R-13 — Una carga reservada no se puede cancelar: el viaje que no ocurre deja todo bloqueado

  • Probabilidad: Media · Impacto: Crítico · Semáforo: 🔴

Evidencia: el estado de la carga no tiene cancelada ni rechazada (smartruck-backend/src/domain/load_status.py:4). El dador solo puede pasar entregada → entrega_confirmada (smartruck-backend/src/application/use_cases/manage_load_by_offerer_use_case.py:44), y el transportista solo puede mover la carga a en_camino, demorada o entregada (smartruck-backend/src/application/use_cases/manage_load_by_transporter_use_case.py:58). El camión queda ocupado hasta que la carga llega a entregada (smartruck-backend/src/application/use_cases/loads/assign_truck_to_load_use_case.py:29 y manage_load_by_transporter_use_case.py:98).

Qué pasa en el negocio: si el viaje se cae (el dador no aparece, la mercadería no está, el transportista se arrepiente), no existe ninguna salida. El transportista queda con el camión bloqueado, una carga reservada que no puede iniciar y el unlock fee pagado. El dador tampoco puede liberar la oferta. Ambos quedan atrapados en un error que el producto no sabe resolver y que se resuelve por teléfono: es el peor momento posible para la reputación.

Mitigación: agregar el estado cancelada con actor y motivo; liberar camión y semirremolque automáticamente; definir la regla de devolución del fee según quién cancela y en qué momento.

🔴 R-07 — El unlock fee no se devuelve y no hay mecanismo de disputa

  • Probabilidad: Media · Impacto: Crítico · Semáforo: 🔴

Evidencia: no existe refund, ni chargeback, ni estado de disputa en el backend (búsqueda de refund, reembolso, chargeback y disputa en smartruck-backend/src: sin resultados). La propuesta sí lo prometía: "si alguna de las dos partes decide retirarse o cancelar por distintos motivos, el dinero será devuelto".

Qué pasa en el negocio: el unlock fee es un pago sin cobertura. Si el transportista paga y el dador no aparece, la plata se pierde. Si el transportista paga y después se arrepiente, la plata se pierde. Cada caso se convierte en un reclamo que la plataforma no tiene cómo contestar, y un reclamo sin respuesta es una razón excelente para volver al canal informal. El fee deja de ser "el precio de acceder a la oportunidad" y pasa a ser "el peaje que se paga por el riesgo".

Mitigación: definir y construir la política de devolución (plazo, responsable, casos); devolver el fee cuando la carga se cancela por responsabilidad del dador; registrar los pagos aprobados sin carga reservada para poder compensarlos.

🔴 R-08 — El estado interno del pago puede divergir del de MercadoPago

  • Probabilidad: Media · Impacto: Crítico · Semáforo: 🔴

Evidencia: la firma del webhook se valida bien (smartruck-backend/src/infrastructure/inbound/http_controllers/payments_controller.py:141) y el unlock revalida contra MercadoPago antes de reservar (smartruck-backend/src/application/use_cases/loads/unlock_load_use_case.py:46). Lo que falta es la reconciliación: no hay ningún barrido del lado del servidor que compare los pagos locales con los del proveedor. La única reparación automática es el webhook, y la única reparación manual es que el transportista siga con la app abierta y llame a POST /payments/{id}/sync (payments_controller.py:203). Además, ProcessPaymentNotificationUseCase.process sobrescribe el estado local con el que informe el proveedor en ese momento, sin impedir una regresión (smartruck-backend/src/application/use_cases/payments/process_payment_notification_use_case.py:19), y la preferencia declara una back_urls.pending (mercadopago_payment_gateway.py:55), o sea que hay métodos de pago cuyo ciclo no llega a approved de inmediato.

Qué pasa en el negocio: si el webhook se pierde, el transportista ya pagó pero el sistema sigue viendo el pago como PENDING: la carga queda bloqueada (R-11) y la oferta muere. Nadie se entera hasta que alguien reclama. Con un pago en estado pending (por ejemplo, una transferencia), el desbloqueo se rechaza hasta que el proveedor lo aprueba, y si el transportista se va, la plata queda en el limbo del proveedor y la carga bloqueada.

Mitigación: barrido de reconciliación periódico que compare pagos locales con MercadoPago y marque los divergentes; no permitir que el estado local retroceda (ignorar notificaciones tardías); manejar explícitamente el estado pending con una espera visible para el usuario en lugar de un rechazo.

🔴 R-12 — La identidad transaccional viene de la URL y las rutas críticas no validan al usuario

  • Probabilidad: Media · Impacto: Crítico · Semáforo: 🔴

Evidencia: las rutas de bloqueo, desbloqueo y abort-lock reciben el transporter_id como parámetro de path y no declaran ninguna dependencia de autenticación (smartruck-backend/src/infrastructure/inbound/http_controllers/loads_controller.py:903 a :943). El API Gateway es público y sin política de seguridad (smartruck-infra/modules/api_gateway/main.tf, "Punto de entrada público SMARTRUCK"), y tampoco tiene rate limiting (la única regla de WAF vive en la zona de Cloudflare y cubre otro host, ver R-26).

Mitigación: aplicar el filtro de vencimiento en la búsqueda con el NotExpiredLoadsFilter que ya existe; barrido periódico de cargas vencidas y bloqueadas huérfanas; mostrar la ventana de tiempo en la tarjeta de oferta.

🟡 R-20 — Inconsistencia entre los números que muestra el producto y los que usa el sistema

  • Probabilidad: Media · Impacto: Medio · Semáforo: 🟡

Evidencia: la calculadora de retorno del portal del transportista usa constantes fijas: gasoil 1.200 $/L, consumo 30 L/100km, peaje 35.000 (smartruck-transportista/src/domain/empty-return-cost.ts:2). El backend usa otros valores: gasoil 2.000 $/L y 0,3 L/km (smartruck-backend/src/application/use_cases/loads/search_loads_use_case.py:15), y tarifa de 2.000 ARS/km (smartruck-backend/src/domain/models/pricing.py:4). Además, el monto estimado que ve el transportista es el max_price que puso el dador, no un precio de mercado (search_loads_use_case.py:177). El propio archivo de la calculadora aclara que es un cálculo provisional hasta que lo haga la API.

Qué pasa en el negocio: el producto muestra dos precios de combustible y dos tarifas por kilómetro, y un estimado de ingreso que es el techo del rango del dador. La promesa de ahorro —el argumento de venta central— se calcula con supuestos que el propio sistema contradice. Un transportista que chequee los números (y los transportistas chequean los números: es su oficio) encuentra la contradicción y pierde confianza en todo el resto.

Mitigación: que la calculadora consuma los mismos valores que usa el backend, o que el backend exponga un endpoint de simulación; mostrar el supuesto con su fecha de vigencia; mostrar un estimado de mercado en lugar del techo del dador.

🟡 R-33 — No hay procedimiento de recuperación ante pérdida de datos

  • Probabilidad: Baja · Impacto: Crítico · Semáforo: 🟡

Evidencia: en el repositorio no hay ningún script de backup ni de restore, ni el pipeline documenta un snapshot previo a las migraciones (R-23). La base vive en Supabase, con los respaldos del proveedor, pero no hay procedimiento propio que definir qué se restaura, en qué orden y con qué criterios.

Qué pasa en el negocio: una pérdida o corrupción de la base no solo borra las cargas: borra el historial de viajes, las calificaciones y la reputación, que es el activo que justifica quedarse en la plataforma. Sin el historial, el producto vuelve a ser un tablón vacío: se pierde el activo de confianza que justificaba el esfuerzo comercial.

Mitigación: documentar el procedimiento de restore y probarlo una vez contra un ambiente de pruebas; definir el punto de recuperación aceptable (RPO/RTO) y verificar que el plan de respaldos del proveedor lo cubra; versionar un export de los datos de negocio críticos.

Metodología de trabajo aplicada

Para el desarrollo del proyecto se adoptó un marco de trabajo ágil e híbrido que combinó elementos de Scrum para la gestión, planificación y seguimiento del proceso, con prácticas de Extreme Programming (XP) orientadas a asegurar la calidad técnica del software. En la práctica, el proceso evolucionó hacia un sistema mixto y pragmático, adaptado al contexto académico y a la estructura horizontal del equipo de estudiantes, sin constituir una implementación ortodoxa de ninguna de las metodologías mencionadas.

Scrum se utilizó como referencia para organizar el trabajo mediante un backlog priorizado, historias de usuario, estimaciones y entregas incrementales. De XP se incorporaron prácticas vinculadas con el desarrollo guiado por pruebas de aceptación, la integración frecuente, los commits atómicos y la refactorización. La aplicación de estas prácticas se adaptó a las características del equipo, con responsabilidades distribuidas y sin la asignación de roles rígidos.

El objetivo de esta metodología fue mantener una evolución continua del producto, facilitar la validación temprana de los requerimientos, mejorar la trazabilidad entre las necesidades y su implementación y establecer condiciones verificables para asegurar la calidad de cada incremento de software.

Marcos de gestión y organización del trabajo

Product backlog e historias de usuario

La planificación del producto se organizó a partir de un conjunto de historias de usuario registradas en el repositorio roadmap, dentro de la plataforma GitHub. Estas historias se agruparon en épicas, representadas mediante milestones, y se vincularon con los repositorios de producto correspondientes.

El backlog funcionó como un artefacto dinámico que permitió organizar los requerimientos, priorizarlos y mantener la trazabilidad entre las necesidades funcionales, los cambios de código y los resultados obtenidos. La prioridad y el alcance de las historias se revisaron durante el desarrollo en función de las dependencias técnicas, los resultados de las validaciones y la retroalimentación recibida del equipo y de los tutores.

Las historias se utilizaron como unidad principal de planificación y seguimiento. Para su identificación y organización se emplearon referencias asociadas a las épicas como prefijo del nombre. Las historias asociadas al desarrollo de interfaces mantuvieron la referencia a sus correspondientes historias de backend cuando esa división resultó útil para conservar la trazabilidad. Cuando la separación dejaba de aportar cohesión, el trabajo se organizó como una única historia. Así, los requerimientos pudieron relacionarse con sus criterios de aceptación, los cambios de código y los commits asociados.

Sprints y entregas incrementales

El trabajo se organizó mediante sprints y entregas incrementales orientadas a obtener funcionalidades verificables durante el ciclo de desarrollo. La propuesta inicial contemplaba iteraciones de dos semanas, pero en la práctica los ciclos tuvieron una duración aproximada de una semana, determinada principalmente por las demostraciones que el equipo realizaba ante los tutores.

Los sprints funcionaron como referencia para organizar la planificación, el desarrollo, la revisión y la validación de los incrementos. El alcance se ajustó durante el ciclo cuando las necesidades del proyecto lo requirieron, manteniendo como referencia el valor de negocio definido.

Este enfoque reemplazó la dependencia de una única entrega final por una secuencia de incrementos que se verificaron progresivamente en los distintos ambientes. De esta manera, los problemas pudieron detectarse con anticipación y los ajustes se incorporaron durante el desarrollo.

Planificación, estimación y seguimiento

Durante el refinamiento de las historias se definieron los criterios de aceptación, las dependencias, la prioridad y la estimación relativa del esfuerzo. La planificación organizó el trabajo de acuerdo con su valor, su complejidad y las condiciones necesarias para comenzar la implementación.

La estimación distinguió dos dimensiones complementarias:

  • US Points: representaron una estimación relativa de la complejidad, la incertidumbre y el esfuerzo asociado a una historia. Se utilizaron durante el refinamiento mediante una escala de Fibonacci acotada.
  • Estimate (hs) y Spent (hs): representaron, respectivamente, las horas previstas al comenzar una historia y las horas efectivamente insumidas al liberar la funcionalidad al ambiente de test.

Esta distinción permitió complementar la estimación relativa con el registro del esfuerzo real. Mientras que los US Points facilitaron la comparación entre historias, las horas permitieron contrastar la previsión inicial con el tiempo de ejecución y mejorar las estimaciones futuras.

Cuando una historia presentó un alcance o una complejidad excesivos, se evaluó su división en sub-historias. En particular, la documentación de estimación estableció que las historias de 8 puntos o más debían analizarse para decidir si convenía dividirlas.

Revisión y validación de los incrementos

La revisión del trabajo se integró al flujo de desarrollo mediante la validación de las funcionalidades implementadas y la comprobación de sus criterios de aceptación. Los incrementos se liberaron inicialmente al ambiente de test, donde el equipo verificó el comportamiento del producto antes de promover una versión a producción.

La retroalimentación del equipo y de los tutores permitió ajustar las prioridades y revisar el alcance de los requerimientos en cada semana. Si bien la propuesta inicial contemplaba ceremonias formalizadas de Sprint Review, demostraciones y retrospectivas con una duración determinada, el proceso aplicado se centró en las actividades efectivas de planificación, revisión y validación, sin establecer una duración u horario obligatorio para todas estas instancias. Esta decisión respondió a los solapamientos entre las responsabilidades externas de los integrantes.

La mejora continua se abordó mediante el análisis de los resultados del desarrollo, las dificultades detectadas y la información obtenida durante las validaciones. En las retrospectivas realizadas se utilizó un tablero de Miro con notas anónimas organizadas en tres categorías: qué se debía mantener, qué se debía mejorar y qué se podía incorporar o innovar.

Prácticas de ingeniería del software

Desarrollo guiado por criterios de aceptación

Los criterios de aceptación de las historias de backend se expresaron mediante escenarios Gherkin en español. Estos escenarios describieron el comportamiento esperado de las funcionalidades utilizando un lenguaje compartido entre los requerimientos, la implementación y la validación.

Antes de que una historia de backend quedara preparada para su desarrollo, los archivos .feature debían estar versionados en main y vinculados desde el ticket correspondiente. Los escenarios ejercitaban la aplicación en el paso Cuando y comprobaban el resultado esperado mediante Entonces.

De esta manera, los criterios de aceptación se utilizaron como una referencia verificable para determinar si la funcionalidad implementada cumplía con el comportamiento esperado. Esta práctica incorporó principios de desarrollo guiado por comportamiento (BDD) y redujo las ambigüedades entre las necesidades expresadas y su implementación técnica.

Integración, pruebas y despliegue

La integración frecuente se implementó mediante trabajo directo sobre main, commits atómicos y una convención uniforme de mensajes. A diferencia de la propuesta inicial, el flujo aplicado no utilizó ramas de feature ni pull requests. Las versiones se liberaron progresivamente a los ambientes de test y producción mediante los scripts de release definidos para los repositorios de producto.

La propuesta original también contemplaba pipelines con etapas específicas de compilación, análisis estático, pruebas automatizadas, detección de secretos y smoke tests posteriores al despliegue. Estas técnicas se aplicaron según las capacidades del repositorio o servicio correspondiente, sin considerarlas un requisito uniforme para todo el proyecto. La validación común consistió en ejecutar la suite de pruebas acordada, verificar los criterios de aceptación en test y confirmar la promoción del incremento a producción.

Infraestructura como código

La gestión de infraestructura incorporó el uso de Infrastructure as Code (IaC), con el objetivo de describir y versionar programáticamente la configuración de los entornos de plataforma.

La documentación de los templates de infraestructura evidencia el uso de Terraform y su integración con procesos automatizados mediante GitHub Actions. Estas herramientas permitieron reproducir configuraciones, mantener un historial de cambios y reducir la dependencia de modificaciones manuales sobre los recursos de infraestructura. La aplicación de estas prácticas se atribuye a los repositorios y componentes donde están implementadas, sin extenderla automáticamente a todos los servicios del sistema.

Refactorización y código limpio

La mantenibilidad del software se promovió mediante commits atómicos, integración frecuente y refactorización cuando fue necesario. Estas prácticas mejoraron la estructura interna del código sin alterar el comportamiento funcional esperado.

En los servicios que documentan explícitamente estos criterios se utilizó una arquitectura hexagonal y principios de código limpio para favorecer la separación de responsabilidades, la claridad de las dependencias y la facilidad de mantenimiento. La revisión de la documentación técnica también formó parte de las actividades de calidad cuando los cambios introducidos afectaron su contenido.

Definición de preparado (Definition of Ready)

La Definition of Ready (DoR) estableció las condiciones mínimas que debía cumplir una historia antes de ingresar a la etapa de desarrollo. Su objetivo fue evitar que se iniciaran trabajos con requerimientos ambiguos, dependencias sin resolver o estimaciones pendientes.

Para que una historia pudiera comenzar, debía cumplir con los siguientes requisitos:

  1. Identificación y descripción: título, descripción contextualizada en formato de historia de usuario, épica, identificador y prioridad asignados.
  2. Criterios de aceptación: escenarios Gherkin en español, versionados en main y enlazados desde el ticket para las historias de backend. En los spikes se indicó explícitamente cuando estos criterios no aplicaban.
  3. Vinculación entre historias relacionadas: referencia explícita a la historia de backend correspondiente en las historias de interfaz cuando existía esa relación.
  4. Estimación del esfuerzo: US Points cargados durante el refinamiento mediante la escala de Fibonacci utilizada por el equipo.
  5. Análisis de dependencias: dependencias técnicas y funcionales identificadas y desbloqueadas antes de comenzar la implementación.
  6. Estimación inicial en horas: campo Estimate (hs) registrado al pasar la historia al estado In progress.

Los requisitos específicos de cada historia se complementaron con información de diseño, prototipos, contratos de API, estructuras de datos o análisis de microservicios afectados cuando el requerimiento lo necesitó. Estos elementos no constituyeron condiciones generales obligatorias para todas las historias.

Definición de terminado (Definition of Done)

La Definition of Done (DoD) estableció las condiciones que debía cumplir una historia para considerarse finalizada. El cierre no dependió exclusivamente de terminar la implementación, sino también de verificar el comportamiento, integrar el código y liberar efectivamente el incremento.

Una historia se consideró terminada cuando cumplía con las siguientes condiciones:

  1. Criterios de aceptación satisfechos: todos los escenarios aplicables finalizaban correctamente.
  2. Código y pruebas integrados: los cambios se encontraban integrados en main, manteniendo la trazabilidad mediante el historial de commits.
  3. Pruebas ejecutadas satisfactoriamente: la suite acordada finalizaba correctamente, de acuerdo con las características del servicio y del requerimiento.
  4. Liberación y validación en test: la funcionalidad se encontraba liberada en test y había sido validada por el equipo.
  5. Esfuerzo real registrado: las horas efectivamente insumidas estaban cargadas en el campo Spent (hs).
  6. Documentación actualizada: se habían actualizado el README, las especificaciones técnicas o los contratos de API cuando los cambios los afectaban.
  7. Promoción a producción: el equipo había promovido la versión a prod mediante el release correspondiente al ciclo de trabajo.

Por lo tanto, en el proceso aplicado, el estado Done no equivalió únicamente a haber terminado la implementación ni a disponer de una funcionalidad en test. Una historia alcanzó este estado cuando el incremento fue validado, se registró el esfuerzo real, se actualizó la documentación afectada y se completó su promoción a producción.

Estas definiciones se aplicaron como criterios de referencia y no de manera purista. Los trabajos de reestilizado, correcciones y otras tareas de mantenimiento no siempre contaron con una épica asociada a una funcionalidad nueva. En esos casos se mantuvieron los controles pertinentes de trazabilidad, validación, registro del esfuerzo y documentación, adaptando el formato del ticket a la naturaleza del trabajo.

Organización de los estados y trazabilidad

El seguimiento de las historias se realizó mediante estados que reflejaron su avance:

  • una historia preparada pasó a In progress al comenzar su implementación;
  • una vez desarrollada y verificada, se liberó a test y pasó a In review;
  • durante esa etapa se registraron las horas reales y se validaron los criterios de aceptación;
  • cuando el equipo confirmó el incremento y promovió la versión a producción, la historia pasó a Done.

Este flujo permitió distinguir la implementación de una funcionalidad, su validación en un ambiente intermedio y su liberación definitiva. La relación entre épicas, historias, repositorios, escenarios Gherkin y commits mantuvo la trazabilidad entre los requerimientos y su implementación. A su vez, los campos de estimación y esfuerzo real aportaron información para analizar la ejecución del trabajo y mejorar las decisiones de planificación.

Síntesis del enfoque metodológico

La metodología aplicada combinó una organización incremental del trabajo con prácticas de ingeniería destinadas a mantener la calidad y la trazabilidad del software. La gestión basada en historias de usuario, épicas, prioridades y estimaciones permitió estructurar el backlog y ajustar el alcance durante el desarrollo. Gherkin, la integración frecuente, los commits atómicos, las pruebas y la refactorización establecieron mecanismos de verificación y mantenimiento del producto.

La separación entre los ambientes main, test y prod organizó la liberación progresiva de los incrementos, mientras que las definiciones de preparado y terminado establecieron condiciones explícitas para comenzar y cerrar las historias.

Si bien el proceso no siguió estrictamente una única metodología ágil, conservó los principios de adaptabilidad, colaboración, entrega incremental y mejora continua. La metodología resultante se definió por la combinación de mecanismos de gestión y prácticas técnicas que permitieron organizar el desarrollo, validar los resultados y considerar terminadas las funcionalidades únicamente después de su validación y despliegue en producción.

Jerarquía de trabajo

Todo el trabajo se modela como user stories en el repo smartruck-ar/roadmap, agrupadas en épicas (milestones) y planificadas en el Board del sprint. No hay tasks: cada historia se trabaja directamente en el repo de producto que corresponde.

Modelo

Épica       milestone de roadmap         D.2 - Gestión de carga
  └── Historia   issue "user story"      D.2.8 - Como dador, Quiero …, Para …
        ├── Contraparte de UI            UI-D.2.8 - Como dador, Quiero …, Para …
        └── Sub-historia (sub-issue)     D.2.8.1 - …

Prefijos

El prefijo sale del milestone y se hereda en toda la cadena.

PrefijoProducto o grupoMilestones
DDadorD.1 … D.7, D.X
TTransportistaT.1 … T.7, T.X
RServicio de rutasR.1
BBackofficeBackoffice
SSpikes (contador único, sin producto)SPIKES

NivelFormatoEjemploQuién lo asigna

Historia de UIUI-<épica>.<M> - <título>UI-T.3.14 - Como transportista, …La automatización (prefijo UI- en el título o tags front+back / crear front)

La historia de backend y su contraparte de UI comparten el número: el contador es único por milestone. Una vez numerado, el título no cambia.

Qué lleva cada nivel

Épica (milestone)

  • Objetivo de negocio amplio que agrupa historias.
  • No se estima ni tiene repositorio.

Historia (user story)

  • Título Como …, Quiero …, Para …; la automatización le agrega el número y el label user story.
  • Backend: los criterios de aceptación son sus escenarios Gherkin (Plantilla de ticket).
  • UI (UI-): referencia la historia de backend asociada.
  • En el Board lleva Status, Sprint, US Points, Priority, Estimate (hs) y Spent (hs).
  • Se trabaja en el repo de producto que corresponde, en main (Workflow de entrega).

Spike

  • Investigación o decisión con un entregable concreto (documento o decisión), sin código de producto.
  • Milestone SPIKES y label spike. Gherkins: no aplica.

Completitud

Done implica ambiente productivo. Detalle en DoD.

NivelSe completa cuando…
HistoriaEstá liberada a prod con el release del sprint
ÉpicaTodas sus historias están Done

Definition of Ready (DoR)

Una historia solo entra a desarrollo si cumple este checklist. Recién ahí pasa a Ready en el Board.

Historia lista para trabajar (Ready)

  • Issue en roadmap con milestone y número asignado por la automatización
  • Título Como …, Quiero …, Para … y contexto en la descripción (Plantilla de ticket)
  • Backend: Gherkins pusheados a main del repo y link al .feature en la descripción
  • UI: referencia a la historia de backend asociada
  • US Points cargados (Estimación)
  • Priority asignada
  • Dependencias declaradas (Bloqueado por #<N>) y desbloqueadas

Gherkins

En una historia de backend, los criterios de aceptación son sus escenarios Gherkin. Los .feature tienen que estar pusheados a main antes de considerarla Ready, y la descripción tiene que tener el link al archivo. El formato del feature sigue la Convención de Gherkin. Si no aplica (spike), indicar Gherkins: no aplica.

Ciclo de vida en la descripción de una user story de backend: al crearla, los escenarios van escritos en la descripción; antes de Ready se pushean a main; una vez en main, el bloque se reemplaza por el link al .feature. Detalle en Plantilla de ticket.

Al comenzar la historia

  • Pasarla a In progress en el Board
  • Cargar Estimate (hs) (horas hombre previstas)

Eso es distinto de los US points: los puntos son esfuerzo relativo; las horas son la estimación temporal al arrancar.

Definition of Done (DoD)

Una historia está Done cuando está en ambiente productivo. Una épica está Done cuando todas sus historias lo están.

Regla de oro

Done = en productivo (además de cumplir CA y tests). Productivo se libera a mano, con el equipo, al final del sprint (Workflow de entrega).

Estado en el BoardSignifica
In progressEn desarrollo en main
In reviewLiberado a test con release_to_test y pipeline en verde
DoneLiberado a prod con release_to_prod al final del sprint
NivelDone cuando…
HistoriaEstá desplegada en productivo y cumple el checklist de abajo
Épica (milestone)Todas sus historias están Done

Historia Done

  • Cumple todos los criterios de aceptación (escenarios Gherkin en verde, sin @wip)
  • Código pusheado a main del repositorio asociado
  • Tests acordados en verde (incl. aceptación / Gherkin si aplica)
  • Validada en test (historia en In review)
  • Desplegada en ambiente productivo con el release del sprint
  • Spent (hs) cargado con las horas hombre insumidas
  • README del repo y docs actualizados si aplica

  • Número de la historia en el scope de los commits (Conventional Commits)

Workflow de entrega

Cómo una historia pasa de Ready a producción. No hay ramas de feature ni pull requests: se trabaja en main y los ambientes se mueven con los scripts de release.

Quick path

  1. Tomar una historia Ready del Board y pasarla a In progress.
  2. Implementar en main, con commits atómicos y un push por commit (Conventional Commits).
  3. Con la feature terminada y la suite en verde, liberar a test: ./scripts/release_to_test patch|minor|major.
  4. Con el pipeline de test en verde, pasar la historia a In review y cargar las horas insumidas.
  5. Al final del sprint, el equipo valida todo en test y libera a prod: ./scripts/release_to_prod. Las historias liberadas pasan a Done.

Ramas y ambientes

RamaPara quéCómo se mueve
mainIntegración. Acá se trabajaPush directo, un push por commit
testAmbiente de test./scripts/release_to_test patch|minor|major
prodAmbiente productivo./scripts/release_to_prod, a mano, con el equipo, al final del sprint

Nunca se pushea a mano a test ni a prod. Los repos de documentación y soporte (docs, roadmap, smartruck-ai, smartruck-infra, audit) solo tienen main y no se liberan.

Release a test

release_to_test corre desde main limpio y al día:

  1. Sube la versión (patch, minor o major).
  2. Commitea tag:vX.Y.Z y crea el tag.
  3. Pushea main y test de forma atómica. El pipeline de test despliega esa versión.
Cambio desde la última versiónNivel
Solo correccionespatch
Funcionalidad nueva compatibleminor
Contrato roto (API o esquema incompatible)major

Release a prod

release_to_prod no crea versión nueva: promueve lo que está en test a prod. Exige que main y test apunten al mismo commit. Lo corre el equipo al final del sprint, con todo validado en test.

  • README del repo y docs actualizados si el cambio los afecta

Desarrollo con agentes

Cómo arrancar y llevar una feature con un agente de IA (Claude Code u OpenCode) usando el setup del repo smartruck-ai.

Quick path

  1. Instalar el setup siguiendo la guía de instalación del README de smartruck-ai.
  2. Abrir el agente con el wrapper de la carpeta de repos: <carpeta>/bin/claude-smartruck o <carpeta>/bin/opencode-smartruck.
  3. Pasarle la historia del Board:
/nueva-feature roadmap#<N>

Fases

FaseQué hace el agente
1. PreparaciónActualiza todos los repos de la organización y docs. Lee la historia y asegura los criterios de aceptación. Actualiza los Gherkins en el .feature del repo (con @wip) y en el ticket. Pasa la historia a In progress.
2. GateMuestra el plan (escenarios, capas, archivos y decisiones abiertas) y espera la aprobación. Es la única pausa.

Conventional Commits

Convención de mensajes de commit del equipo, basada en Conventional Commits 1.0.0.

Formato

<type>(<historia>): <descripción>
  • type: solo feat, fix o refactor
  • scope: número de la historia de roadmap (ej. D.2.8, T.3.12, B.5). La contraparte de UI usa el mismo número, sin UI-
  • descripción: resumen corto en imperativo / presente

Tipos permitidos

TypeCuándo usarlo
featNueva funcionalidad / feature
fixCorrección de un comportamiento incorrecto
refactorCambio de código sin cambiar comportamiento observable

No usamos otros types (chore, docs, test, etc.) en este proyecto.

Ejemplos

feat(D.2.8): agregar caso de uso para eliminar una carga

fix(T.2.11): corregir el camión asignado en el detalle de la carga

refactor(B.5): extraer el mapeo de estado del transportista

Commits atómicos y push

  • Un commit es la unidad más chica que tiene sentido sola y deja el repo funcionando: un ciclo de TDD, un script, una página.
  • El test va en el mismo commit que el código que verifica.
  • Cada commit se pushea apenas se crea. No se acumulan commits locales.
  • Todo se pushea a main: no hay ramas de feature ni pull requests. test y prod solo se mueven con los scripts de release (Workflow de entrega).
  • Sin cuerpo ni trailers (Co-authored-by, Signed-off-by), sin --no-verify y sin force-push.
  • En los repos sin historias (smartruck-ai, docs) o sin historia asociada, el mensaje va sin scope: feat: <descripción>.

Checklist

  • Type es feat, fix o refactor
  • Scope es el número de la historia
  • Descripción clara y acotada al cambio
  • Commit atómico y pusheado a main

Convención de logging (arquitectura hexagonal)

Dónde y qué loguear en los servicios SmartTruck (backend y fronts con capas hexagonales).

Los logs se emiten con LogManager (application/logger/): JSON a stdout. La recolección (Datadog, Loki, etc.) es responsabilidad de la infraestructura, no de un provider en la app. Convención de carpetas: Arquitectura backend.

En smartruck-backend, los controllers/repos de infrastructure inyectan LogManager (desde application.logger). Cada controller y cada repositorio lo recibe por Depends (por ejemplo trucks_controller.py y PostgreSQLTruckRepository); este módulo solo provee el mecanismo.

API (sin secretos)

LogManager(service="smartruck-backend", env="test").info("…")
LogManager(service="smartruck-backend", env="test").error("…")

Niveles disponibles: fatal, error, warn, info, debug, trace.

NivelUso
infoQué se está haciendo en bordes (entrada/salida, datos salientes seguros)
error / warn / fatalFallos y advertencias (p. ej. GlobalExceptionHandler)
debug / traceSolo para depurar; no para flujo de negocio habitual

Solo message: str. No hay parámetros password, token ni similares: no loguear secretos en el mensaje.

Correlation ID

  • Header: X-Correlation-Id
  • Middleware: reutiliza el header o genera un UUID; lo refleja en la response.
  • LogManager lo incluye en el JSON cuando está disponible (correlation_id).

Dónde loguear

Solo en los bordes del hexágono: entradas y salidas.

LugarRol en el hexágonoQué loguea
Controladores (adapters de entrada / HTTP)Entradainfo de lo que se está haciendo (request / caso, sin secretos)
Repositorios (adapters de salida / persistencia u otros gateways)Salidainfo de operaciones hacia afuera
GlobalExceptionHandlerBorde HTTPerror/warning de excepciones burbujeadas + response HTTP
[HTTP] → Controlador ──info────────────┐
              │                        │
              ▼                        ├──> stdout → Datadog / audit
         Caso de uso                   │
              │                        │
              ▼                        │
         Repositorio ──info────────────┤
              │                        │
              └── excepciones ──► GlobalExceptionHandler ──error─┘

Errores y excepciones

  • Las excepciones burbujean hasta un GlobalExceptionHandler (capa HTTP / inbound).
  • El handler centraliza: log error/warning, mapeo a response HTTP. Los controllers no atrapan para relanzar.
  • Controllers: solo info de entrada (y datos seguros). Repos: info de salida; propagan errores hacia arriba.
  • No duplicar el log de error en repo y controller y handler.

Info / “qué se está haciendo”

  • Controlador: entrada al caso (ej. “crear viaje”, IDs relevantes, sin secretos).
  • Repositorio: operación de salida (ej. “persistir load”, “buscar oferente por email”).
  • Preferir mensajes estructurados (JSON) con service, env, level, y contexto útil (request_id si existe).

Qué no loguear ahí

EvitarMotivo
Loguear en cada línea del caso de uso / dominioRuido; el dominio queda limpio
Loguear el mismo error en repo y controller y handlerDuplicado; el error se loguea una sola vez en el GlobalExceptionHandler
Passwords, tokens, PII innecesariaSeguridad

Excepción: decisiones de negocio que el spec pide registrar

Un caso de uso puede emitir un warn cuando el spec pide dejar registro de una decisión de negocio para poder investigarla después. Por ejemplo, el caso de uso de recomendaciones deja una línea por cada carga que descarta, con su id y el motivo. El caso de uso recibe LogManager por constructor, y el motivo lo describe el dominio (DiscardedLoad). Es un warn por decisión, no un log por línea: no es ruido.

Checklist

  • info en controlador (entrada) y repositorio (salida)
  • Errores/excepciones logueados en el GlobalExceptionHandler (no catch/rethrow en controllers)
  • Sin logs de negocio ruidosos en application/domain (salvo las decisiones que el spec pide registrar)
  • Salida a stdout (JSON vía LogManager)
  • Sin passwords/tokens en la API ni en el contenido del mensaje

Automatización de historias (roadmap)

Cómo crear una historia de usuario y qué formas hay de que el propio repositorio la numere, la etiquete y arme la contraparte de front/back automáticamente.

Repo: todo esto pasa en smartruck-ar/roadmap. Nunca en smartruck-backend, smartruck-dador, smartruck-transportista ni ningún otro repo de producto — esos repos no tienen esta automatización.

Implementación: .github/workflows/auto-number-issues.yml + scripts/auto_number_issues.py, corriendo en el runner self-hosted del repo.

Qué dispara la automatización

Dos eventos de GitHub sobre una issue de roadmap:

EventoCuándo pasaQué hace
milestonedSe le asigna un milestone a la issueNumera, etiqueta y evalúa si hay que crear una contraparte
labeledSe agrega uno de los tags front+back, crear front o crear backSolo reacciona a esos tres; cualquier otro label (bug, user story, etc.) se ignora

Nada de esto pasa si la issue no tiene milestone asignado.

Comportamiento por defecto (una sola historia)

Al milestonear una historia sin ningún tag especial, la automatización:

  1. La numera: <Prefijo del milestone>.<siguiente número> - <título> (ej. T.2.9 - Como transportista...).
  2. Le agrega el label user story.
  3. La agrega al proyecto Board (#4) y le asigna el sprint actual (según fecha de Argentina).

Esto es todo. No crea ninguna otra historia. Si querés una contraparte de front o de back, tenés que pedirla explícitamente con los tags de la sección siguiente.

El item queda con Status: Backlog (el default de GitHub para un item nuevo). Movelo vos a Ready/In progress en el Board — la automatización no lo hace.

¿Cómo indico si la historia es de backend o de UI?

No hay un tag para esto: se define con el título, antes de milestonear.

  • Backend (default): título normal, sin prefijo. Ej: Como transportista, Quiero filtrar cargas... → queda T.2.9 - Como transportista....
  • UI: escribí el título arrancando con UI-. Ej: UI-Como transportista, Quiero filtrar cargas... → queda UI-T.2.9 - Como transportista....

El número (T.2.9) sale de un contador compartido por milestone: da lo mismo si la última historia numerada en ese milestone fue de backend o de UI, la siguiente sigue la secuencia.

Crear las dos historias (back + UI) de una

Si de entrada sabés que la historia necesita pantalla y backend:

  1. Escribí el título (con o sin UI-, según cuál de las dos querés que sea "la original").
  2. Agregале el label front+back (antes o después de milestonear, da igual el orden).
  3. Milestoneala.

Resultado: la historia original queda numerada, y se crea una segunda issue con el mismo número y el prefijo que le falta (si la original era de backend, la nueva es UI-T.2.9 - ...; si la original ya era UI-, la nueva es la de backend). Quedan linkeadas entre sí con un comentario cruzado (🔗 Relacionado con el ticket de UI/backend: #N).

Al terminar, el tag front+back se saca automáticamente de la historia original. Las dos terminan solo con user story.

Agregar la contraparte más tarde

Si ya tenés una historia numerada (de backend o de UI) y después decidís que también necesita la otra mitad, no hace falta recrear nada: agregale el tag correspondiente a la historia que ya existe.

Tengo...Le pongo el tag...Y se crea...
Una historia de backend (T.2.9 - ...)crear frontSu contraparte de UI (UI-T.2.9 - ...), mismo milestone, sprint actual
Una historia de UI (UI-T.2.9 - ...)crear backSu contraparte de backend (T.2.9 - ...), mismo milestone, sprint actual

El tag usado se saca solo al terminar. Si lo ponés en el lado que no corresponde (ej. crear front sobre una historia que ya es de UI), no hace nada más que sacarse el tag — no rompe nada ni duplica.

Si la historia todavía no tiene milestone asignado, el tag no dispara nada (no hay de dónde sacar el número); hay que milestonearla primero.

Milestones de spike (SPIKES, T.SPIKE)

Los spikes son un caso aparte: no se separan por producto (transportista/dador) y nunca generan contraparte, tengan o no alguno de los tags anteriores.

  • Prefijo fijo: S, con un contador único compartido por todos los milestones de spike (no hay S para transportista y otro para dador).
  • Se numeran igual que cualquier historia (S.1 - ..., S.2 - ..., …), reciben user story y sprint actual.
  • Los tags front+back, crear front y crear back se ignoran por completo en un milestone de spike.

Sub-issues (una historia que cuelga de otra)

Si la historia que estás milestoneando es sub-issue de otra issue del propio repo roadmap (relación nativa de GitHub, no un link a mano), hereda el prefijo del padre en vez de calcular uno nuevo a partir del milestone:

Padre  T.1.1  (ya numerada)
  └── Hijo  T.1.1.1, T.1.1.2, …   (siguiente número dentro del padre)

Si el padre todavía no tiene un prefijo numerado (por ejemplo, no fue milestoneado todavía), el hijo se numera como una historia normal a partir del milestone.

Una vez numerada, el título queda fijo

Si el título ya tiene un prefijo numerado (con o sin UI- adelante), la automatización nunca lo recalcula ni lo renombra, sin importar cuántas veces se vuelva a milestonear o etiquetar la issue. Esto es lo que hace seguro:

  • Re-milestonear por error una historia ya numerada (no la duplica ni le cambia el número).
  • Agregar crear front/crear back sobre algo que ya tiene su contraparte (find_existing_companion la detecta por un marcador oculto en el body y no crea una segunda).

Decisiones tomadas

  • Wordmark como texto, no como imagen. El header del dador dejó de usar smartruck-logo.jpg y renderiza el wordmark con el componente compartido src/components/layout/wordmark.tsx, usado tanto por el header autenticado como por el bloque de marca de las vistas públicas. Razón: un JPG escalado en proyector se ve borroso, el texto queda nítido a cualquier tamaño, y el brief pide una fuente propia para el título "Smartruck", cosa que solo aplica a texto. El JPG se mantiene como favicon y og:image.
  • El wordmark es bicolor y oblicuo, como el logo. "Smar" en --brand-blue y "Truck" en --brand-green, en Chakra Petch bold italic (@fontsource/chakra-petch/700-italic.css; Chakra Petch llega hasta 700, no existe el 900). Los dos tramos van en spans adyacentes sin espacio entre sí, para que un lector de pantalla lea una sola palabra.
  • El subrayado de la marca es una "frenada". Al pasar el mouse entra rápido y se asienta: la barra va sesgada a skewX(-10deg) para seguir la itálica y se pasa un 5% antes de volver, así que se lee como un vehículo frenando y no como un barrido. Es el swoosh que ya tiene el logo. Con prefers-reduced-motion aparece sin animación.
  • Cuidado con scale en Tailwind v4. El subrayado está escrito como CSS propio (.wordmark-underline en src/styles.css) y no con utilidades a propósito: Tailwind v4 emite scale-x-* a través de la propiedad independiente scale, que compone con transform, así que un after:scale-x-0 de base cancela cualquier keyframe que anime transform y el subrayado queda invisible. Lo mismo rompe un transition-transform cuando lo que cambia es scale. Lección para el portado: si una animación anima transform, no la mezcles con utilidades de escala.
  • La marca lleva al inicio solo dentro del shell autenticado. En el header es un Link a / con cursor pointer; en el bloque de marca de las vistas públicas queda como texto, sin interacción. El componente Wordmark sigue siendo presentacional: el link está en el Topbar.
  • Los dos colores de marca son los del logo: azul petróleo rgb(10 52 68) = #0a3444 en --brand-blue, y verde oliva rgb(101 105 68) = #656944 en --brand-green. Definidos en oklch() con el rgb de origen en comentario, y registrados como --color-brand-blue / --color-brand-green para que existan las utilidades text-brand-blue / text-brand-green. En modo oscuro los dos se elevan (#6b9aaf y #aab07d): el azul del logo es ilegible sobre una superficie petróleo, así que se conserva el hue y se sube la luminosidad.
  • El primario del dador es un verde más fuerte que el del logo, no el oliva literal. --primary, --ring y las variantes de sidebar usan oklch(0.51 0.1 130) = #53712f (5.57:1 con blanco encima, 4.87:1 contra el fondo); en oscuro oklch(0.64 0.11 130) = #76994f.

2. Metodología y dinámica que seguimos (esto es lo que hay que respetar)

  1. Commits atómicos, sin push. Formato conventional commits <type>(<id-task>): <descripción>, con type limitado a feat / fix / refactor. Un commit = un cambio revisable y autoexplicativo. Nada se pushea sin pedido explícito.
  2. Gate de verificación por task, obligatorio. scripts/run_lint + scripts/run_all_tests + npm run build, todo en verde. En Windows los scripts son bash y WSL no trae node: hay que correrlos con Git Bash (& "C:\Program Files\Git\bin\bash.exe" -lc "./scripts/run_all_tests"). CI=true los vuelve check-only (no mutan).
  3. Normalizar ANTES de commitear. El gate corre prettier --write / eslint --fix: si commiteás primero y normalizás después, el árbol queda sucio y hay que rehacer commits.
  4. Los tests de presentación son puntos de decisión, no bloqueantes. Un restyle puede cambiar lo que un test fija, pero entonces el test se actualiza en el mismo commit y a propósito. Lo prohibido es romperlo en silencio. Hay aserciones que fijan implementación y no valor para el usuario y conviene reescribirlas (ejemplo real: un findAllByText("Transportista asignado")).toHaveLength(2) que congelaba una duplicación card/overlay; se cambió a findByText(...) en el commit que deduplicó).
  5. Presentación ≠ comportamiento. El restyling no cambia flujos, validaciones, navegación ni contratos de red. Cuando un pedido sí toca comportamiento (ej. caché), se documenta y se decide aparte.
  6. git status antes de delegar o commitear. Una vez el árbol tenía ediciones sin commitear de una persona y se commiteó sin querer. Si hay cambios que no son tuyos: parar y reportar.
  7. Tokens antes que componentes. Nada de familias crudas de Tailwind (emerald-*, sky-*, …); todo por tokens semánticos en src/styles.css (:root / .dark, mapeados en @theme inline). Nada de px fijos (text-[Npx], w-[Npx], …): la escala se maneja con html { font-size: 142.9% } y todo es rem-based.
  8. Tres roles de radio y nada más: Pill (rounded-full) para lo accionable, Panel (rounded-2xl) para lo que contiene, Inset (rounded-xl) para lo que va dentro de un panel. Un hijo nunca puede quedar más redondo que su contenedor.
  9. Regla de superficies: fondo de página beige (--background), toda superficie que contiene campos en --card, y ningún campo interactivo resolviendo al fondo de página.
  10. Sin iconos decorativos en headers. Se retira un icono si al quitarlo no se pierde información; se conserva sólo si codifica dirección o estado.

4.1 Contrato de fechas: normalizar aware → local Argentina naive (CRÍTICO)

Qué pasa. El backend declara las fechas de carga como hora local argentina naive: pickup_date y delivery_deadline se persisten en columnas TIMESTAMP WITHOUT TIME ZONE.

Evidencia relevada:

  • src/infrastructure/outbound/time/system_date_time_provider.py — el "ahora" del dominio es datetime.now(ARGENTINA).replace(tzinfo=None).
  • src/infrastructure/outbound/persistence/models/load.py y migrations/versions/0001_initial_schema.py — columnas sa.DateTime() (naive).
  • El test de aceptación exige eco exacto: test/acceptance/.../crear_oferta_carga_steps.py manda "2026-08-20T08:00:00" y espera el mismo string.

Qué rompía. El portal dador serializaba la hora del picker (wall clock naive) con offset -03:00. Al castear un timestamptz a una columna naive con la sesión en UTC, Postgres guardaba +3h (12:00 → 15:00). El dato quedaba mal persistido (por eso también lo veía mal el transportista, que sólo lee). El bug afectaba toda hora cargada, no sólo el default.

Qué ya se hizo (del lado dador, en smartruck-dador). Se corrigió el serializador para emitir hora local naive sin offset ni Z (toBackendLocalDateTime en src/lib/date.ts, con test unitario). Los envíos nuevos llegan correctos.

Qué falta del lado backend (red de seguridad). El backend sigue aceptando strings con offset de cualquier cliente. La recomendación es un validador de entrada que normalice a hora local argentina naive antes de que el valor llegue al caso de uso. Punto de entrada relevado: src/infrastructure/inbound/http/.../create_load_request.py (pickup_date: datetime, delivery_deadline: datetime).

Comportamiento propuesto:

si el datetime viene aware  → astimezone(America/Argentina).replace(tzinfo=None)
si viene naive              → dejarlo igual (comportamiento actual, no romper clientes)

Criterios de aceptación sugeridos:

  • CA1: un pickup_date con offset (2026-09-20T12:00:00-03:00) se persiste y se devuelve como 2026-09-20T12:00:00 (hora local argentina), no 15:00.
  • CA2: un pickup_date naive sigue comportándose exactamente como hoy (el contrato de eco exacto del test de aceptación no cambia).
  • CA3: aplica a pickup_date y delivery_deadline por igual.
  • CA4: existe un test de aceptación que manda un datetime con offset y verifica el eco; hoy la suite sólo manda naive, que es justamente por lo que el bug no se detectó.
